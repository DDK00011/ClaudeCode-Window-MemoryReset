# 2026-07-06 — Preserving active Codex sessions

## Issue
- MemoryReset could include active Codex sessions among cleanup targets and terminate them.
- In particular, the Codex CLI run in VS Code was directly matched by the existing `codex.exe` / `node_repl.exe` whitelist and became a termination target, while Codex on Antigravity happened to survive because its execution path/parent structure differed.

## Root cause
- `Get-TargetProcesses` directly contained Codex CLI collection logic within the Claude/Antigravity recovery tool.
- In the `-IncludeDescendants` and final `taskkill /T` paths, even when Codex was not a direct target, it could be killed with parent tree termination.

## Changes
- Fully excluding Codex from cleanup targets did not meet the requirement, so the approach was discarded.
- Added `Test-IsCodexProcess`, `Get-CodexRootPids`:
  - `codex.exe`
  - `node_repl.exe`
  - `@openai/codex`
  - `OpenAI\Codex`
- Codex CLI root is included in cleanup targets again.
- `Update-ActivityState` aggregates CPU/I/O counters across the entire Codex process tree instead of looking only at the Codex root.
- `Update-ActivityState` is called again immediately before calculating `-IdleOnly` candidates and actual termination to block the path that kills active Codex from a stale idle state.
- `Stop-TargetProcesses` skips only Codex trees without tracking history or not yet proven idle, even before `CloseMainWindow`.
- To prevent Codex `node.exe` root from being misclassified as Claude `node.exe` orphans, `-OrphansOnly` / `Get-ReclaimCandidates` excludes Codex from the immediate termination path for orphans.
- Added regressions to `Test-Patterns.ps1` for the Codex active guard, tree CPU/I/O tracking, orphan exclusion, and empty-array double-wrap.
