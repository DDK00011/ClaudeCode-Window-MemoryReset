# 2026-07-06 — Preserving active Codex sessions

## Issue
- MemoryReset could include active Codex sessions among cleanup targets and terminate them.
- In particular, the Codex CLI run in VS Code was directly matched by the existing `codex.exe` / `node_repl.exe` whitelist and became a termination target, while Codex on Antigravity happened to survive because its execution path/parent structure differed.

## Root cause
- `Get-TargetProcesses` directly contained Codex CLI collection logic within the Claude/Antigravity recovery tool.
- In the `-IncludeDescendants` and final `taskkill /T` paths, even when Codex was not a direct target, it could be killed with parent tree termination.

## Changes
- Fully excluding Codex from cleanup targets did not meet the requirement, so the approach was discarded.
- Added `Test-IsCodexProcess`, `Get-CodexRootPids`:
  - `codex.exe`
  - `node_repl.exe`
  - `@openai/codex`
  - `OpenAI\Codex`
- Codex CLI root is included in cleanup targets again.
- `Update-ActivityState` sums CPU counters across the entire Codex process tree rather than looking only at the Codex root, and records I/O counters as diagnostic values.
- `Update-ActivityState` is called again immediately before calculating `-IdleOnly` candidates and actual termination to block the path that kills active Codex from a stale idle state.
- `Stop-TargetProcesses` skips only Codex trees without tracking history or not yet proven idle, even before `CloseMainWindow`.
- To prevent Codex `node.exe` root from being misclassified as Claude `node.exe` orphans, `-OrphansOnly` / `Get-ReclaimCandidates` excludes Codex from the immediate termination path for orphans.
- `Test-Patterns.ps1` adds active Codex guard, tree CPU tracking, orphan exclusion, and empty array double-wrap regression checks.

## Additional fix — idle Codex not recovered after sleep

### Issue
- Codex sessions finished more than 5 hours ago met the `idleMinutes` condition but did not become cleanup candidates.
- There was sleep/resume in between, and after resuming, the Codex `lastActiveAt` was advanced to the current time in the `TrackActivity` tick, returning the candidate count to 0.

### Root cause
- The earlier Codex protection improvement used increases in Codex tree I/O counters as a condition for updating `lastActiveAt`.
- I/O-only changes such as sleep resume, IPC, logs, and background file handle cleanup were recorded as "activity" despite not being actual work, resetting idle time.

### Changes
- `Update-ActivityState` uses only Codex tree CPU delta to determine activity.
- `lastIoOps` / `lastIoBytes` continue to be recorded but are retained only for diagnostics and do not update `lastActiveAt`.
- Existing version state already polluted by I/O-only is conservatively corrected only when it lacks `activityModel`, has `lastActiveAt == lastSeenAt`, and has CPU rate below the threshold.
- An ambiguous legacy state does not set `activityModel`, allowing observation again with the new CPU model on the next tick.
- Parent processes with active Codex descendants are excluded before `CloseMainWindow`.
- Immediately before force `taskkill /T`, the process snapshot and active Codex protected PIDs are recalculated.
- `activity-state.json` writes complete JSON to a temporary file then replaces it, and reading retries 1 time to reduce state becoming empty from partial JSON during concurrent scheduled runs.

### Structural decision
- Not a temporary exception. This is a root fix that changes the activity model of `Update-ActivityState`, shared by termination targets/candidates/final termination guard.
- The Codex protection guard in `Stop-TargetProcesses` remains, so sessions with newly observed CPU activity are preserved immediately before termination as well.

### Additional adversarial review findings
- 1st review: after confirming the blocker that the legacy correction condition was too narrow and that recording `activityModel` in correction-failed state eliminates later correction opportunities, this was fixed.
- 2nd review: after confirming the blocker that active Codex descendant protection was only at the force stage and could be closed first by graceful close, it was moved to a filter before `CloseMainWindow`.
- 2nd review: After confirming the blocker that a read failure while directly writing `activity-state.json` could proceed with an empty state, fixed it with retry + temp replace saves.
- During work, the 09:30 automatic `TrackActivity` ran once from an intermediate version, updating local `activity-state.json` to an empty state. This file is a git-excluded runtime file, and new history accumulates from subsequent tick runs.

## Additional Fix — Main Executable Logging

### Issue
- hidden scheduled cleanup did not preserve console output, so its `CloseMainWindow`, Codex protection skip, and `taskkill` results could not be verified afterward.
- Existing `tracker.log` recorded only candidate counts, while `recovery-history.csv` recorded only total terminations, leaving no individual PID/classification/idle-orphan reason for incidents such as `ProcessesKilled=52`.

### Changes
- Added `Write-RunLog`: appends key execution flow to `memoryreset.log`.
- For every main cleanup run, records mode, raw/final target count, target PID/PPID/name/category/WorkingSet/start time/path, and idle/orphan reasons.
- Added logs to `Stop-TargetProcesses` for Codex guard skip, `CloseMainWindow`, no-window, wait, survivor count, and `taskkill` success/already-terminated/failure results.
- When recovery completes, records mode, target count, before/after free MB, recovered MB, and elapsed sec.

### Structural decision
- Not a temporary measure. Rather than newly capturing scheduled task stdout, it writes file logs directly in the shared path where actual termination decisions occur, preventing a root-cause tracking gap.
- `memoryreset.log` continues to use the existing `.gitignore` protection for `*.log`, so personal runtime records are not committed.
